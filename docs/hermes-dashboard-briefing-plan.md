# Hermes 업무 브리핑 섹션 기획안

작성일: 2026년 10월 7일 · 검토용 초안

관제 대시보드 상단에 **Hermes 업무 브리핑**을 배치한다. 사용자가 질문하기 전에 업무 변화를 점검하고, 지금 중요한 일과 그 이유, 다음 행동을 제시한다. 사용자는 대시보드를 열고 30초 안에 오늘의 우선순위를 파악하고 실행할 업무를 선택할 수 있어야 한다.

Hostinger VPS의 Hermes가 화면을 닫은 동안에도 정기적으로 점검하고, 관제 서비스는 저장된 최신 브리핑을 보여준다. 첫 버전은 내 업무의 요약과 계획 제안에 집중한다. 업무 변경은 기존 서비스의 실행 경로를 통해 처리한다.

## 현재 서비스와 연결 지점

| 구분 | 현재 코드에서 확인한 내용 | 기획에 반영할 사항 |
| --- | --- | --- |
| 화면 | 제목 → 위험 알림 띠 → KPI → 업무 목록과 우측 AI 패널 | 제목 바로 아래에 브리핑을 추가 |
| 개인 AI 비서 | Gemini 기반 대화, 근거 자료, 제안 작업 처리 | 상단 브리핑에서 기존 대화 패널로 연결 |
| AI 저장소 | `ai_conversation`, `ai_message`, `ai_action` | 대화와 실행 제안은 재사용하고 정기 브리핑은 별도 저장 |
| 업무 데이터 | 기업, 과제, 통합 마감, 알림, 업무일지 | 기업 업무와 개인 업무일지를 함께 분석 |
| 내 과제 범위 | 기업의 주담당 컨설턴트 중심 필터 | 직접 배정된 과제와 기업 관리 책임을 구분 |
| 권한 | `ai.assistant.use`, 개인·팀 범위, 개별 작업 권한 | 조회·생성·실행 시 현재 권한을 각각 확인 |
| 운영 환경 | Hermes가 Hostinger VPS에 설치되어 있다는 사용자 설명 | 설치 제품·버전·API 설정은 연동 착수 시 확인 |

저장소에 Hermes 연결 코드는 확인되지 않았다. 위 항목은 로컬 코드 기준이며 운영 DB에 마이그레이션이 적용되었는지는 별도 확인 대상이다. 기존 AI 채팅은 `GEMINI_API_KEY`를 기준으로 활성화되므로 Hermes 브리핑의 연결 상태와 분리해야 한다.

## 사용자가 경험할 하루

1. 오전에 접속하면 전날 미완료 업무, 오늘 일정, 임박 마감이 반영된 브리핑을 읽는다.
2. 우선 업무 세 개 중 하나를 열고, 필요한 후속 업무를 등록하거나 기존 과제에서 처리한다.
3. 업무를 완료하거나 기한을 변경하면 다음 점검에서 해당 항목과 계획이 갱신된다.
4. 오후에는 새 위험과 오전 이후의 변경사항을 확인한다.
5. 퇴근 전에는 완료 업무, 남은 일, 내일 먼저 할 일을 확인한다.

‘계속 체크한다’는 표현은 **화면 접속 여부와 관계없는 정기 점검**을 뜻한다. 초기 버전의 점검 간격을 화면과 설정에 명시해 실시간 감시로 오해하지 않게 한다.

## 상단 화면 구성

기본 순서는 **대시보드 제목 → Hermes 업무 브리핑 → 기존 위험 알림 → KPI → 상세 업무 목록**으로 한다. 브리핑에는 여러 업무의 우선순위와 행동을, 기존 알림에는 가장 긴급한 단일 항목을 표시한다. 중복되는 상세 설명은 브리핑에서 줄인다. 기한 초과 등 최상위 경고는 접힌 브리핑에서도 보이며, 작은 화면에서 브리핑이 길어지면 위험 알림을 카드 위로 올린다.

| 영역 | 표시 내용 | 인터랙션 |
| --- | --- | --- |
| 헤더 | Hermes 업무 브리핑, 내 업무/팀 업무, 최근 점검 시각 | 다시 점검, 접기 |
| 핵심 요약 | 현재 상황과 오늘 집중할 일 2~3문장 | 전체 브리핑 열기 |
| 우선 업무 | 최대 3개, 기업명·업무명·D-day·우선 이유·다음 행동 | 해당 업무 열기 |
| 오늘의 계획 | 먼저 / 다음 / 이후의 순서와 준비할 일 | 계획 상세 보기 |
| 변경사항 | 직전 점검 이후 완료·추가·마감 변경 | 변경 근거 보기 |
| 후속 질문 | 오늘 계획 다시 짜기, 이 업무 자세히 보기 | 기존 AI 패널에 브리핑 문맥 전달 |

데스크톱 기본 높이는 약 260~320px을 시작값으로 검토한다. 요약을 왼쪽, 우선 업무를 오른쪽에 배치하고 상세 계획은 펼쳐서 읽는다. 모바일에서는 요약과 최우선 업무 1개를 먼저 보여주고 나머지는 ‘우선 업무 더 보기’로 확장한다. 접힘 상태는 사용자별로 기억한다.

첨부 화면의 어두운 배경과 글자 위계를 유지한다. Hermes의 기본 카드는 중립적인 배경을 사용하고 노랑·빨강은 실제 위험에만 사용한다. ‘정상’ 표시는 색상뿐 아니라 텍스트로 표현하고, 항상 움직이는 처리 애니메이션은 실제 실행 중일 때만 보여준다.

### 화면 문구 예시

아래는 첨부 이미지의 업무명을 활용한 예시이며 실제 추가 업무나 진행 상태를 확인한 결과는 아니다.

> **Hermes 업무 브리핑** · 내 업무 · 최근 점검 09:10
>
> 타이어플라이 주식회사의 SNS 콘텐츠 자동화 전략 수립 과제가 이틀 뒤 마감됩니다. 오늘은 과제의 현재 진행 상태를 확인하고 남은 작업을 정리하는 것을 먼저 제안합니다.
>
> **먼저 할 일** — SNS 콘텐츠 자동화 전략 수립 · D-2  
> 우선 이유: 마감이 2일 남았습니다.  
> 다음 행동: 과제 상세에서 미완료 항목과 제출 준비 상태를 확인하세요.
>
> **계획 제안** — 진행 상태 확인 → 남은 작업 정리 → 제출 전 검토
>
> [업무 열기] [계획 자세히 보기] [Hermes에 이어서 질문]

‘자료가 누락되었습니다’처럼 데이터에 없는 사실을 단정하지 않는다. 확인되지 않은 사항은 ‘확인이 필요합니다’로 표현하고 제안과 관측 사실을 구별한다.

## 브리핑과 계획의 기능 정의

| 기능 | 입력 | 결과 | 제공 단계 |
| --- | --- | --- | --- |
| 오늘의 브리핑 | 미완료 과제, 마감, 일정, 개인 업무일지 | 핵심 요약과 우선 업무 3개 | 1차 |
| 업무 점검 | 직전 스냅샷과 현재 상태 | 완료·추가·기한 변경·새 위험 | 1차 |
| 계획 제안 | 우선 업무와 확인된 일정 | 수행 순서와 다음 행동 | 1차 |
| 마감 브리핑 | 당일 완료·미완료, 다음 날 일정 | 오늘 회고와 내일 우선순위 | 1차 |
| 주간 계획 | 이번 주 마감과 미완료 업무 | 주간 집중 업무와 예상 병목 | 2차 |
| 실행 제안 | 브리핑의 후속 업무 | 과제 생성·수정 등의 검토 가능한 초안 | 2차 |
| 개인화 | 사용자가 명시한 근무 시간과 선호 | 브리핑 시각과 계획 순서 조정 | 2차 |
| 외부 연동 | 별도로 연결한 일정·메일 등 | 외부 정보를 포함한 요약 | 후속 |

계획은 기본적으로 순서만 제안한다. 소요 시간이나 가용 시간이 없는 경우 임의의 시간표를 확정하지 않는다. 시간 배분 기능을 추가할 때는 사용자 입력 또는 명시된 추정값을 사용한다. 완료 집계는 상태 변경 이력이나 점검 간 비교에 근거하고, `updated_at`만으로 ‘오늘 완료’라고 판단하지 않는다.

### 내 업무의 범위

- **직접 수행할 업무:** 접근 가능한 기업의 과제 중 `assignee_id`가 본인인 과제와 본인의 `todo_note`.
- **관리할 업무:** 본인이 주담당인 기업의 마감·인증·일정과 다른 담당자가 수행 중인 과제의 위험. 직접 수행할 업무와 별도 라벨로 표시한다.
- **누락 방지:** 본인 주담당 기업이 아니어도 본인에게 배정된 과제는 접근 권한이 있으면 포함한다. 기업 미지정 일정은 소유·참석자 기준을 확인할 수 있을 때 포함한다.
- **팀 범위:** 현재 대시보드의 팀 조회 권한을 따르되 개인 업무일지 권한을 별도로 적용한다. 현재 업무일지의 팀 조회는 owner 기준이므로 manager의 팀 대시보드 접근 권한만으로 타인의 업무일지를 포함하지 않는다.

기업·과제·마감 뷰에서 같은 업무가 중복 집계되지 않도록 원본 종류와 ID로 통합한다. 개인 화면에는 개인 브리핑을, 팀 화면에는 별도 생성한 팀 브리핑을 표시한다. 범위 전환 시 이전 범위의 내용을 잠시라도 재사용하지 않는다.

### 우선순위 산정

초기 규칙은 기한 초과 → 당일 마감 → 3일 이내 마감 → 7일 이내 마감 → 나머지 업무 순서로 한다. 동일 구간에서는 사용자가 지정한 중요도와 기한을 우선하고, 정체 기간은 보조 신호로 사용한다. 담당 미배정은 관리 행동으로 따로 제시한다.

숫자·D-day·완료 여부는 서버가 계산한다. Hermes는 이 결과를 바탕으로 이유와 행동을 설명한다. 장기간 수정되지 않은 항목은 ‘진행 확인 필요’로 제시하고 실제로 막혔다고 단정하지 않는다. 기간 기준의 초기 제안값은 3영업일이며 운영 피드백으로 조정한다.

## 자동 점검 정책

다음은 초기 운영값 제안이며 모두 한국 시간 기준이다.

| 시점 | 동작 | 모델 호출 정책 |
| --- | --- | --- |
| 평일 08:30 | 아침 브리핑 생성 | 정기 생성 |
| 평일 09:00~18:00, 15분 간격 | 업무 상태 비교와 위험 확인 | 의미 있는 변화가 있을 때 생성 |
| 평일 18:00 | 오늘의 마감 브리핑 생성 | 정기 생성, 동시간대 점검과 통합 |
| 야간·주말 1시간 간격 | 기한 초과·임박 위험 변화 확인 | 새로운 중요 위험이 있을 때 생성 |
| 사용자가 다시 점검 클릭 | 최신 스냅샷으로 점검 예약 | 변화 없으면 기존 결과 유지 가능 |

페이지를 열 때는 저장된 결과부터 보여주고, 오래된 경우 백그라운드 점검을 예약한다. 화면 조회 자체는 모델 호출을 발생시키지 않는다. 점검 작업은 사용자·범위별로 한 번에 하나만 실행하며 수동 요청은 60초 이내 중복을 합친다.

완료, 재개, 신규 배정, 기한 변경, 중요 메모 변경, D-day 구간 변경을 재생성 조건으로 삼는다. 원본 수정이 없어도 날짜가 바뀌면 기한 위험이 달라지므로 날짜를 비교 기준에 포함한다. 삭제·담당 이관·권한 회수도 캐시 무효화 조건으로 처리한다.

## Hostinger VPS 연동 구조

권장 구성은 **관제 서버가 업무 접근을 통제하고, VPS 작업자가 정기 분석을 수행하며, 검증된 결과를 관제 DB에 저장하는 방식**이다. 브라우저는 관제 서버에만 접근한다. 긴 분석이 페이지 응답을 지연시키지 않도록 브리핑 생성은 비동기로 처리한다.

1. 관제 서버에 정기·수동 점검 요청을 저장한다.
2. VPS의 작업자가 전용 인증을 통해 실행 가능한 요청을 가져온다. 요청을 가져올 때 실행 소유권과 유효 시간을 설정한다.
3. 관제 서버가 요청에 등록된 사용자·기업·권한 범위로 업무 스냅샷을 구성한다.
4. VPS 작업자가 로컬 Hermes에 스냅샷과 브리핑 형식을 전달한다.
5. 작업자가 결과를 관제 서버에 반환한다. 서버는 구조·원본 참조·현재 권한·요청 버전을 검증하고 저장한다.
6. 대시보드는 최신 결과를 표시한다. 첫 버전에서는 화면이 보일 때만 30초 간격으로 완료 여부를 확인하고, 이후 필요하면 실시간 구독을 적용한다.

이 구조에서는 브리핑을 위해 Hermes API를 인터넷에 직접 공개할 필요가 없다. 정기 예약의 원장은 한 곳에 두고, VPS의 스케줄러가 예약된 사용자별 요청을 등록하는 방식으로 시작한다. 재시작 후에는 같은 예약 시각의 요청을 중복 생성하지 않으며, 놓친 예약은 최신 시점으로 한 번 보충한다.

설치된 제품이 **Nous Research Hermes Agent**라면 공식 문서의 예약 실행과 API 서버를 연동 후보로 활용할 수 있다. 공식 API는 OpenAI 호환 HTTP 요청을 제공한다. 설치 버전에서 지원되는 범위를 확인한 뒤 로컬 API 또는 CLI 어댑터를 선택한다. 이는 현재 VPS의 기능을 확인했다는 의미는 아니다. [Hermes API 서버](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server), [예약 실행](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron/)

### 기존 채팅과의 연결

상단 브리핑은 자동 생성된 읽기 화면이며, 기존 우측 AI 패널은 후속 질문과 상세 검토에 사용한다. 첫 버전에서 Gemini 채팅을 유지한다면 버튼을 ‘브리핑에 대해 질문’으로 표시한다. **‘Hermes에 이어서 질문’이라는 이름은 실제 대화도 Hermes로 연결한 이후 사용한다.**

전달 문맥은 브리핑 ID, 데이터 기준 시각, 선택 업무 ID, 사용자 질문이다. 대화 서버가 이를 현재 권한으로 다시 조회한다. 모델 응답 문자열을 URL로 전달하거나 화면에 표시된 내용을 최신 업무 상태로 간주하지 않는다.

## 저장 데이터와 서비스 계약

다음 이름과 경로는 구현 시 사용할 수 있는 제안이다. 기존 기능으로 오해하지 않도록 실제 구현 단계에서 확정한다.

| 데이터 | 주요 내용 |
| --- | --- |
| `ai_briefing` | tenant, 사용자, 조회 범위, 종류, 요약, 우선 업무, 계획, 변경사항, 원본 참조, 데이터 기준 시각, 생성 시각, 입력 해시 |
| `ai_briefing_job` | 요청 주체, 범위, 예약 시각, 상태, 중복 방지 키, 실행 소유권, 시도 횟수, 오류, 완료 시각 |
| `ai_briefing_preference` | 자동 점검 사용 여부, 시간대, 점검 시간, 사용자 명시 선호 |
| 상태 스냅샷 | 완료·삭제·재배정을 비교할 최소 필드와 원본 ID, 데이터 버전 |

브리핑 결과에는 `summary`, `priorities`, `plan`, `changes`, `sources`, `dataAsOf`, `generatedAt`를 포함한다. 우선 업무별로 원본 ID, 이유, 다음 행동, 확인 필요 여부를 저장한다. 링크는 서버가 허용한 원본 ID에서 생성한다. 목록 조회 한도로 입력이 일부만 포함되면 전체 건수와 분석 건수를 구분하고 ‘일부 업무 기준’으로 표시한다.

| 제안 API | 역할 |
| --- | --- |
| `GET /api/assistant/briefings/latest` | 인증된 사용자의 유효한 최신 브리핑 조회 |
| `POST /api/assistant/briefings/refresh` | 점검 요청 저장 후 요청 ID 반환 |
| `GET /api/assistant/briefings/jobs/:id` | 본인 점검 상태 확인 |
| `POST /api/internal/hermes/jobs/claim` | VPS 작업자에게 허용된 작업 할당 |
| `POST /api/internal/hermes/jobs/:id/result` | 할당된 작업 결과 검증과 저장 |

VPS 전용 인증은 작업자 식별과 허용 범위에 한정한다. 브라우저에서 보낸 tenant·사용자 ID를 신뢰하지 않으며, 작업자도 임의 사용자의 데이터를 요청할 수 없도록 등록된 작업에 묶는다. VPS에 Supabase 전체 접근 키를 배포하지 않는다. 공유 Hermes 인스턴스를 사용한다면 사용자별 세션·메모리·파일 저장 범위를 분리하고 브리핑 실행에는 필요한 읽기 도구만 부여한다.

기존 `ai_action`은 과제 생성·수정, 기업 메모 추가, 캠페인 초안을 지원한다. 이후 브리핑에서 이 작업을 제안할 수 있지만 원본을 직접 수정하지는 않는다. 사용자가 변경 내용을 검토해 적용하면 기존 권한과 원본 버전을 다시 검사한다. 개인 업무일지 등록은 현재 지원 작업 목록에 없으므로 별도 작업 유형과 검증이 필요하다.

## 연결 상태와 실패 경험

| 상태 | 화면 표시 | 동작 |
| --- | --- | --- |
| 최초 실행 | 첫 브리핑을 준비하고 있습니다 | 기존 관제 업무 목록은 즉시 제공 |
| 정상 대기 | 최근 점검 09:10 · 다음 점검 09:25 | 실제 성공한 점검 시각 표시 |
| 분석 중 | 업무 변경사항을 확인하고 있습니다 | 마지막 정상 결과 유지 |
| 변화 없음 | 09:25 점검 완료 · 변경사항 없음 | 요약 생성 시각은 별도로 유지 |
| 갱신 지연 | 최신 점검이 지연되고 있습니다 | 마지막 성공 시각과 다시 점검 표시 |
| 연결 실패 | Hermes 연결을 확인해 주세요 | 기존 결과에 오래된 정보 표시 |
| 데이터 부족 | 아직 요약할 업무가 없습니다 | 업무 등록 또는 업무일지로 이동 |
| 일부 조회 실패 | 일부 업무를 불러오지 못했습니다 | 누락 범위를 명시하고 전체 정상으로 표시하지 않음 |
| 권한 없음 | 기능 숨김 또는 사용 권한 안내 | 이전 결과도 반환하지 않음 |

‘다음 예약 시각 + 5분’이 지나도 점검 성공 기록이 없으면 갱신 지연으로 처리한다. 작업자 연결 상태, 최근 데이터 점검 시각, 요약 생성 시각을 구분한다. 정상 접속 표시만으로 업무를 확인했다고 표현하지 않는다.

실패 시 최대 3회 제한 재시도 후 마지막 정상 결과를 유지한다. 더 오래된 작업이 나중에 끝나도 최신 결과를 덮어쓰지 않는다. 원본이 변경된 동안 생성된 결과는 오래된 기준임을 표시하고 다음 점검을 예약한다. 권한이 회수되거나 담당 범위가 달라지면 영향받는 결과는 재생성 전까지 숨긴다.

## 1차 출시 범위와 진행 순서

| 순서 | 산출물 | 완료 조건 |
| --- | --- | --- |
| 연동 확인 | VPS 제품·버전, 실행 방식, 모델 공급자, 서비스 통신 경로 확인 | 샘플 업무로 한 번 생성하고 결과 형식 검증 |
| 화면 설계 | 상단 카드와 접힘·모바일·실패 상태 시안 | 30초 안에 우선 업무와 다음 행동을 찾을 수 있음 |
| 데이터 연결 | 내 업무 범위, 상태 비교, 브리핑·작업 저장소 | 본인 배정과 관리 책임이 구분되고 누락·중복이 없음 |
| 자동 실행 | 정기 점검, 수동 갱신, 아침·마감 요약 | 브라우저 종료 상태와 VPS 재시작 후에도 점검 |
| 시범 운영 | 실제 사용자 업무로 1주간 확인 | 근거 오류·중복·누락·비용을 점검하고 운영값 조정 |

1차 출시에는 개인 자동 브리핑, 우선 업무 3개, 순서형 계획, 변경사항, 아침·마감 요약, 수동 갱신, 근거 링크, 기존 채팅 연결을 포함한다. 팀 자동 브리핑, 과제 변경 제안, 주간 회고, 외부 메일·일정 연결은 후속 단계로 둔다. 구현 일정은 VPS 연동 시험 이후 확정한다.

### 출시 검증 기준

- 완료된 업무가 다음 성공 점검에서 우선 목록에서 빠지고, 재개한 업무는 다시 검토된다.
- 원본 수정 없이 날짜만 바뀌어도 D-day와 마감 위험이 갱신된다.
- 주담당이 아닌 기업의 본인 배정 과제도 권한 범위 안에서 포함된다.
- 업무 조회 일부가 실패했을 때 ‘할 일 없음’이나 ‘정상’으로 표시하지 않는다.
- 내 과제와 팀 과제 전환, 담당 이관, 권한 회수에서 이전 범위 데이터가 노출되지 않는다.
- 중복 요청·작업자 재시작·결과 순서 역전에서 중복 브리핑이나 오래된 결과 덮어쓰기가 없다.
- VPS가 중단되어도 대시보드의 기존 업무 기능이 동작하고 최근 성공 시각이 보인다.
- 브리핑의 수치와 원본 링크가 데이터 기준 시점과 일치한다.

운영 지표는 점검 성공률, 갱신 지연 시간, 근거 오류 건수, 브리핑에서 업무로 이동한 비율, 계획의 유용성 피드백, 사용자당 모델 사용량으로 한다. 첫 주는 기준선을 수집하고 수치 목표를 정한다. 모델 비용은 실제 입력·출력 토큰과 선택한 공급자 단가로 계산한다. 변경 없는 정기 점검에는 모델을 호출하지 않고 사용자별 호출 상한을 둔다.

## 구현 전에 확정할 사항

현재 초안은 한국 시간의 평일 업무, 개인 브리핑 우선, 관제 내부 데이터 우선을 기본값으로 삼는다. 연동 착수 시 Hermes의 정확한 제품과 버전, VPS 실행 관리 방식, 사용할 모델, 서비스 간 통신 가능 여부를 확인한다. 제품 검토에서는 근무 시간, 개인 업무일지 포함 여부, 소요 시간 입력 필요성, 팀 브리핑의 공개 범위를 확정한다.
